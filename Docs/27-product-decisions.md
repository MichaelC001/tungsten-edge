## 产品定位

- 钨极首先是一个**窗口任务条**，不是应用启动器，也不是空间管理器。
- 核心价值是让用户一眼看见正在使用的窗口，并能一步切到目标窗口。
- 视觉和交互保持轻量、原生、安静，不为了展示功能增加常驻负担。

## 窗口与位置

- 默认一窗一卡；同一物理窗口里的原生标签只占一个位置，切标签不应新增卡片。
- 最小化、隐藏或窗口暂时读不到时，原来的位置继续保留；只有真正关闭才释放位置。
- 用户排好的顺序应尽量稳定。新窗口靠近同应用的现有窗口，不因刷新或恢复随意跳位。
- 点击当前窗口是切换或最小化，点击其他窗口是直接聚焦目标；操作应立即有轻量反馈，但不能用假高亮误导状态。
- 动作发出去就算数，最终状态以窗口清单为准。有些应用（Illustrator、Electron 系）最小化是异步的，命令收下了但立刻回读还说没生效——不能据此判失败，否则会误判并做出补救动作，反而把窗口拽回来。
- **最小化只应该影响被最小化的那一个窗口**（owner 2026-08-02 定）。A1 收起来之后，本来压在它下面的是谁就轮到谁——是同应用的 A2 就 A2，是别的应用就别的应用。不该有窗口被「凭空抬到最前」。
    - 据此，2026-06-24 定的「最小化后应该回到上一个**别的**应用 B，而不是兄弟窗口 A2」**方向与 owner 本意不符**，作废待改。owner 从没要过这个行为，它是当年为了压住"兄弟窗口冒头"顺手定的目标规则。
    - 但 owner 2026-08-02 决定**本轮不改这条目标规则**，只堵住「无标题的隐形窗口不能当交接目标」这个洞（飞书主窗口被带出来的根因）。理由是改目标规则要引入一个当年没测过的变体——把交接目标改成「A1 正下方那个已被任务条认过的窗口」，同应用兄弟同样有资格；而 `Docs/22` §3.5.4 那张逐帧实测表只测过跨应用交接。风险与收益不匹配。
    - **「兄弟窗口从很后面跳到最前」本轮明确不修**，维持现状。成因是 AppKit 在前台应用的 key 窗口消失时会提拔并硬抬另一个窗口（`Docs/22` §3.5.4 实测：纯最小化时 A2 在 min+245ms 跳到顶）；用系统 Dock 时同应用窗口整组相邻所以看不出来，钨极按单窗口切换、z 序交错，埋得深的兄弟一抬就很显眼。
    - **什么时候重新考虑**：owner 觉得跳前的频率难忍时。动手前必须先钉死一个前提——装机版到底读不读得到 CG 窗口标题（见 `Docs/28`「开发构建的权限归属」条），它决定现有那套交接逻辑现在到底有没有在生效，也就决定了改动的真实影响面。
- 最小化失败时不把焦点抢回原窗口。**代价是**：万一真失败，焦点会停在上一个应用而窗口还立着。这是刻意选的——真失败极罕见，而抢焦点这个动作本身每次都在制造「最小化完又自己弹回来」的毛病（2026-07-20 Illustrator 实测）。
- 窗口没有标题不等于它不是用户窗口。系统设置的真实主窗口可以长期以空标题暴露；坚持“标题必填”会把它降级成应用入口，连窗口级操作和“窗口已就绪”的反馈一起丢掉。因此接受“系统标准窗口语义 + 足够尺寸”作为替代可信信号，代价是承担少量启动瞬态窗误收风险。若以后出现真实负样本，只针对样本补充更强信号；不能退回“所有窗口必须有标题”。

## 必要的应用级入口

- Finder 始终保留一个入口。没有 Finder 窗口时，点击它打开主目录；具体文件夹窗口仍各自显示。
- 消息应用保留稳定入口和未读角标；消息身份决定它显示在消息区（未运行也在、灰色可点击启动），退出后留不留由「在程序坞中保留」统一决定（首次标记即默认勾上、观感不变；取消勾选则退出后从消息区消失、再运行时回来）。收进抽屉才从区中隐藏。额外窗口仍按窗口显示，新弹出的窗口落在窗口区头部（紧邻消息区），不甩到末尾。
- **能不能进消息区，由「认不认得出主窗口」决定（2026-07-21 定）**。消息区的图标代表这个应用的主窗口——点它就等于点那张窗口卡。所以自动识别的条件从「像不像消息应用」收紧成「像消息应用**而且**认得出它的主窗口」：认不出主窗口的应用进来也只会得到一个**只能唤醒、不能收起**的图标，而且它的窗口还会在窗口区重复出现一次。用「能不能被正确表示」当门槛，规则就自洽了，不用为个别应用打补丁。
    - Apple「信息」因此不再自动进消息区。它的窗口标题是一串内部编号（`10691420171100425`），永远不等于应用名，主窗口永远认不出——这笔账从 v0.1.0 的发布说明就记着「Apple Messages 不能通过点图标最小化」，一直没查出原因，2026-07-21 才归因。移出消息区后它就是一张普通窗口卡，点击最小化正常，也不再重复显示。
    - 顺带解决了 Ghostty、隔空投送这类**被误判**的应用：它们只是 App Store 类别恰好是「社交网络」，窗口标题却是命令名或别的，从此自动进不来，不用再手动取消。
    - **一次通过就永久算数，之后不再复检**。微信主窗口关掉时只剩「笔记」窗口，那一刻其实也认不出——若每轮复检，微信就会掉出消息区、开回来又跳进去，「主窗关闭后点图标唤醒」这个日常操作也会一起坏掉。
    - 手动标记不受这道门槛限制：用户执意要把某个应用放进消息区，随他。已经在名单里的应用也不回溯清理（无从判断当初是怎么进去的，硬清有误伤既有配置的风险），需要移出的自己右键「取消标记消息应用」一次即可。
- 无法可靠识别具体窗口的应用，可以退回一个稳定的应用图标，不能为了“一窗一卡”制造假窗口。

## 启动反馈

- 未运行应用的弹跳反馈表达的是“还在等它可用”，不是“已经看到一个进程”。GUI 应用只起了进程、主窗口还没出现时，停掉反馈会让用户以为点击没有生效。
- 兜底从 8 秒放宽到 20 秒（2026-08-01），是为了覆盖剪映、Xcode 这类慢启动应用；代价只是真失败时反馈保留更久。菜单栏应用和明确启动失败不必等满兜底，但不能拿启动初期尚未定型的进程策略当作已就绪证据。

## 保留与位置

- 应用放在任务条还是抽屉，是“位置”；退出后是否继续显示，是「在程序坞中保留」。两者互相独立：拖动只改变位置，勾选或取消勾选只改变退出后的保留状态，任何一个动作都不替用户顺带改变另一个。
- 所有符合条件的普通应用都在右键菜单中显示可勾选的「在程序坞中保留」，当前状态直接由勾表示；不再使用「从程序坞中移除」表达取消保留。
- 应用运行且有真实窗口时，仍显示普通窗口卡片；勾选保留不会把多个窗口压成一个应用图标。
- 同一 bundle 的多进程应用按应用整体决定无窗口兜底（2026-08-05，WPS 实例）：只要任一进程贡献真实窗口，零窗口同伴不再额外显示应用名卡；所有同伴都无窗口时才保留一张应用级入口。原因是 `app-*` 表达的是应用入口而非进程入口，逐进程投影会让 WPS 的两个真实窗口旁再多一张「WPS Office」，多个零窗口进程还会因共享同一 id 生成重复卡。
- 普通保留应用的**应用级次序跨机器重启保持**（2026-08-04，用户 Phoebus 报「重启 mac 后排过序的 app 图标顺序乱掉」）：运行中的多窗口应用仍是一窗一卡，但重启后会按 bundleID 排名把同一应用的当前窗口组成连续块，排在普通临时应用之前；块内不冒充恢复旧窗口次序。消息应用仍归消息区自己的顺序，额外聊天窗继续执行既有「新窗落窗口区头部」规则。
    - **这个排名不是「冷启动时排一次就完」**：开机登录时任务条比多数应用先起来，第一次对账那刻通常只有未运行保留应用的占位图标。排名因此做成了常驻规则——任何时刻出现的、没有位置记忆的卡都按它落位。做成一次性模式的话，「重启后顺序固定」对**开机时已经在运行**的应用完全无效（它们的窗口晚一步到，只能掉到末尾），等于修了一半。
    - **重启后聊天窗仍排在保留图标左边，这是已知且接受的**（owner 2026-08-04 判断）：机器重启后应用是重新打开的，此刻没有应用内的附带窗口，这个场景实际不会发生。**不要当 bug 去"修"**——真要改，改的是 2026-07-12 那条「新弹出窗落窗口区头部」的规则本身，那是另一个决定。
- 已勾选的应用退出，或运行中没有真实窗口时，才在原位置折叠为一个图标；退出状态由图标下方**没有运行点**表达（2026-08-02 起不再变灰，见《界面外观》），点击重新启动。
- Finder 不提供保留状态。**消息应用现在也纳入统一保留勾选**（2026-07-18 反转 7-12 定的「消息身份自带永久、与保留互斥」旧决定）：消息身份只决定显示在消息区，「在程序坞中保留」统一决定退出后留不留，两者可共存。首次手动标记或自动识别为消息应用时默认补上保留（所以升级和日常观感不变），用户之后取消勾选不会被后续扫描重新打开。
- **消息区的退出态与别处一视同仁**（2026-07-19 定，反转「消息区图标一直全亮、随时可点」的旧视觉决定）。当时的做法是「退出即变灰」，2026-08-02 拿掉图标淡化后，统一的表现改成**退出即无运行点**——原则没变（消息区不搞特殊），只是承载信号的地方换了。同一次改动还给所有未启动的应用图标的右键菜单补了首项「打开」（排在最近文件之前），右键即可重新启动。
- 运行点表达的是系统程序坞同类的「当前存在 regular 应用身份」，不是“某个同 bundle helper 进程还活着”。运行态不能只信启动/退出通知：通知丢失后由切换应用、唤醒或解锁触发全量对账；进程死亡仍只认 POSIX 代际，LaunchServices 暂时查不到活进程不能据此撤点。
- **右键菜单的固定次序（2026-07-20 定）**：最近文件 → 动作项（打开 / 显示 / 隐藏 / 新建窗口 / 最小化 / 关闭窗口）→ 成员项（在程序坞中保留 / 标记消息应用）→ **退出恒为最后一项**。以前保留勾选的应用关掉全部窗口后，「退出」会被成员项压到倒数第三，找不到；现在无论卡片、保留图标、消息图标还是抽屉图标，退出永远在菜单最底下。以后往菜单加任何新项，都排在退出之前。

## 抽屉

- 抽屉用于收纳低频应用的位置，一款应用只占一个图标；收进抽屉后，该应用的整个窗口块从任务条隐藏。抽屉成员默认不等于退出后保留。
- 上半区显示正在运行的抽屉应用；下半区只显示未运行但已勾选保留、或仍具消息身份的应用。未勾选的普通抽屉应用退出后暂时隐藏，但保留原抽屉位置和顺序，下次运行时回到原位。
- 任何菜单都不提供“收进抽屉 / 移出抽屉”；位置变化只通过拖动表达。普通抽屉图标使用与窗口卡一致的「在程序坞中保留」勾选项。
- 拖进、拖回和取消拖动都必须可逆，不能出现应用同时消失或两边重复。
- 消息区顺序属于用户的位置记忆，应跨重启保持；消息 chip 可以在区内排序并收进抽屉。消息区图标菜单同时提供「在程序坞中保留」和「标记为消息应用」两项原生勾选——前者改退出后留不留（不改分区），后者才真正移除消息身份、让它离开消息区，仍只清消息身份并记录 opt-out，不动 kept 与抽屉位置。两项标题恒定不变，以勾选状态表达当前是否生效。
- 消息应用收进抽屉时保留消息身份；只有明确取消「标记为消息应用」勾选才取消身份并阻止自动加回，手动重新标记后可以恢复。
- 运行中的消息应用只能从抽屉拖回消息区，未运行消息应用继续留在抽屉；拖到文件夹区、窗口区或桌面不改变成员位置。
- 抽屉图标（外置胶囊上的九宫格预览）悬停和点击都有反馈：悬停时内层九宫格轻微放大、点击回弹，**反馈只作用于里面的九宫格，外框保持静止**；拖卡投放时仍高亮整个胶囊（那是投放目标提示，与悬停/点击是两回事）。九宫格整体略微缩小，避免视觉过满。

## 文件夹与中转格

- 固定文件夹区用于快速浏览和打开常用目录，默认点击是打开或关闭内容弹窗。
- 中转格只保存文件引用，不主动移动或复制文件；失效引用在打开时清理。
- 文件可以拖入中转格、从弹窗拖给其他应用；文件夹可以固定并排序。
- 外部文件拖到固定文件夹 chip 上时，把文件移入该文件夹；同卷移动、跨卷复制并保留来源，目标已存在时不覆盖。落在 chip 间隙或文件夹区尾部的文件仍是静默无操作，只有目录能固定。
- 固定文件夹和中转格共用一个轻量内容弹窗，同一时刻只打开一个。
- **中转站可以在菜单里关掉**（2026-07-30 定，回应 GitHub issue #3 第 2 条「用不上想关掉」）。关掉只是把图标藏起来，已暂存的文件引用照旧保留，勾回来还在。
    - 一开始想做成「空的时候自动隐藏」，你后来改回**手动开关**——自动隐藏会带来一个自相矛盾的状态：藏起来之后就没地方把文件拖进去了，等于关上门把钥匙锁在里面。
    - **已接受的边界**：中转站关掉**而且**一个固定文件夹都没固定时，整个文件夹区（连同分隔线）会消失，此时任务条上没有任何拖文件进来的落点，「添加文件夹…」入口也一起没了——它只挂在中转站和文件夹图标的右键菜单上。回路是菜单里把中转站勾回来。你 2026-07-30 明确接受这个边界，不为它额外造入口。

## 面板与多屏

- **设置改为一页式原生窗口，状态栏菜单继续保留快捷设置**（2026-08-03，反转此前「只用状态栏菜单」的决定）。起因是少数派用户反馈：他按 ⌘, 开出一个**完全空白**的窗口（那是当年为了让框架能编译塞的空占位场景），而钨极的设置全都只活在菜单栏图标里，他没找到，于是「根本设置不了」。状态栏菜单适合日常快速切换，但设置项增多之后既难发现也难理解。现在 `⌘,` 和状态栏「设置…」统一打开完整设置面。
    - **两个面怎么分**（同日定，当天又收窄了一次，见下）：设置窗口放全部偏好；状态栏菜单只留会话中途要随手切的——显隐钨极、两条唤醒滑块、登录时启动、检查更新、设置…、退出。
    - **分工判据最终收敛为「滑块类进菜单，开关类进设置窗口」**（2026-08-03 当天定）：两条唤醒滑块**都从设置窗口移除**，只留在菜单；设置窗口两处各留一行指路，告诉用户去菜单栏图标调。理由是滑块本来就是"随手拖一下看效果"的东西，而系统 Dock 那条一旦两边都有，就要维护**两套互不相干的草稿**并做同步——那是当时新增复杂度里最大的一块，删掉设置窗口那份后 `NativeDockDraftSync` 整个类型连同测试一并消失。**代价**：设置窗口从此不是严格意义上的"完整配置面"，自动隐藏只能在菜单里调；指路文案是唯一的补救，所以必须写清去处（当初那位用户的抱怨正是"找不到设置"）。

    - **复议触发条件**（满足任一即可重开）：macOS 以后提供不需要 root、且早于 Dock 边缘判断的事件接口；后台应用能正式影响全屏下的 Dock 行为；或 owner 接受抬层级、快捷键等「共处」方案。不要再以 session tap 或合成鼠标事件重开。
- **进全屏时任务条闪一下：已知未修（2026-08-06）。** 现象是从非全屏切到全屏的一瞬间，整条任务条先消失 → 又冒出来一下 → 再消失；退出全屏和普通切桌面都不闪。v0.7.6 上存在。
    - **试过并证伪的方向一**：以为是「隐藏得太晚」（判定要等 21ms 的异步探测）。改成在空间切换那一刻同步给出判定后，等待窗口压到 0ms，**闪烁一点没变**——说明系统的空间切换通知本身就晚于肉眼可见的那一刻。技术细节见 `Docs/05-known-platform-quirks.md`《进全屏时任务条闪一下》，试验代码封存在 `parked/fullscreen-flash-skylight`。
    - **试过并证伪的方向二（2026-08-08）**：永久撤掉 `.fullScreenAuxiliary` 与 control 的重叠时间分别约 `769ms / 776ms`，无差别；监听 `AXWindowCreated/Resized` 已能在全屏 CG 窗口前约 18ms 完成分类，但主线程 `orderOut` 仍错过 WindowServer 的过渡快照，约 345ms 重叠仍在。无条件在每次普通窗口创建时先藏会制造新的日常闪烁，不接受。该实验已从主线完整撤回。
    - **为什么先不修**：现有公开信号都晚于 WindowServer 的过渡快照；常驻高频轮询既没有可靠的预测能力，也会新增长期成本。为一个几百毫秒的视觉瑕疵改坏普通新建窗口或增加常驻扫描不划算。
    - **复议触发条件**：有用户反馈这个闪烁；或找到能在 WindowServer 抓取过渡快照前到达、同时能明确区分普通窗口创建与全屏进入的主线程信号。
- 最大化窗口避让（2026-07-16 定案，取代封存的 Option+绿点 / slide 两条旧试验）：任务条常驻可见时，前台铺满窗口的底边**平缓抬到任务条上方**，间距取紧贴（约 2pt，曾定 8pt 后反转）；解除最大化交还应用，不拦缩放键。瞬间 / 平缓两种观感开关对照后，平缓动画胜出为默认。
- 避让跟着任务条走：哪块屏有任务条哪块屏避让，任务条离开即恢复铺满——没有任务条的屏幕上不动用户窗口。只抬**前台应用**的铺满窗口，后台窗口切到前台才处理。
- 与应用的边界：应用自己抢回铺满按"补抬一次、再抢则暂退"处理，之后按秒级节奏自愈重试，任何情况下都不存在永久不抬的状态；用户重新最大化永远当成新的一次操作。已接受的小瑕疵：被抬起的窗口第一次点缩放可能先弹回铺满一次（系统缩放记忆所致），随即会被重新抬起。
- **避让改成可关，而且默认关（2026-08-03 owner 定）**。菜单栏加勾选项「最大化窗口避开任务条」，位置在「鼠标悬停显示应用名」之后。
    - **为什么给开关**：这是全项目唯一会去**改写别人应用窗口尺寸**的功能，且带着一串已接受的瑕疵（缩放键第一次弹回、外接 1x 屏写入迟到、应用抢回铺满时的拉扯）。这类东西该允许用户拒绝，之前只有开发用的环境变量能关，普通用户够不着。
    - **为什么默认关**：没主动选过的人不该被改窗口。代价是明确的——**老用户升级后避让会直接消失**，得自己去菜单勾上；发版说明里要专门点一句，否则会被当成 bug 报回来。
    - **名字**：叫「最大化窗口避开任务条」，不叫内部术语「避让」。同 8/2 悬停改名那次的判断——公开发布的 app，菜单得让没读过说明的人看懂。
    - **自动隐藏档位下不置灰**：避让本来就只在常驻可见时工作，但这一项是偏好不是当前状态，置灰会让人以为功能没了。
    - **取消勾选立刻还原**：已经被抬起来的窗口马上长回原生铺满尺寸，不等下次最大化。
    - 复议触发条件：如果开始有人反馈「装完根本不知道有这个功能」，可以复议改成首次运行提示，或改回默认开。
- 边缘唤醒与自动隐藏统一（2026-07-17，修复网友反馈的贴底边闪烁）：鼠标贴着任务条所在屏幕的最下边缘时——不必正对任务条本体——任务条应保持显示，离开底边才恢复自动隐藏；这一条只在设置了具体唤醒秒数时生效，「不唤醒」和「常驻显示」两种模式行为不受影响。

## 辅助功能权限（2026-07-30 定）

- 权限出问题时**必须说话**。旧版在权限失效时只是静默变成空任务条，用户既不知道发生了什么，也不知道怎么恢复——这是不可接受的默认行为。
- **运行中权限掉了，钨极收起任务条、弹恢复引导，重新授权后自己重启。** 不选「只弹个提示不动任务条」（屏幕上会留一条空条），也不选「只在菜单栏标红」（用户看到的仍然是"突然空了"）。重启是因为原地半启动状态最容易出诡异 bug。
- **「删掉旧权限记录重新添加」只作为条件式建议，等 8 秒才出现，而且永远不能断言「你的旧记录已经失效」。** 我们读不到系统的权限数据库，既证明不了用户有没有打开开关，也证明不了旧记录已经失配。而且固定证书签的包授权是跨版本有效的，文案不能预设签名方式。
- **首次授权和运行中失效是两套文案。** 首次授权成功是当前进程直接继续启动，既没有"自动重启"也没有窗口残留，那些话不该出现在首次授权的引导里。
- **跑在临时/只读位置的副本只当一次性引导壳**：请用户先搬到「应用程序」，期间不接管其他实例、不抢全局快捷键、也不向系统申请权限（否则会在系统里留一条指向"卸载就没"的副本的死记录）。判据是**所在磁盘是否只读**，不是"路径在 /Volumes 下"——后者会误伤把钨极装在移动硬盘上的用户；读写型磁盘映像因此漏拦，这是有意接受的。
- **已接受的边界**：用户走「退出钨极 → 删旧权限记录 → 手动重开」这条路时，之前被任务条让开过的窗口会停在矮一条的状态，重开也不会自动复位。引导里明说"重新最大化一次就复原了"。不为这条冷门路径做状态持久化——认错了反而会改坏用户的窗口。
- 判断权限有没有真生效，**看程序坞里有没有钨极图标**（没有=生效）。系统设置里的开关状态不作数。

## 界面外观（2026-07-30 定）

- **浅色和深色各有一套视觉数值，深色这套定稿不再动。** 整套观感原本只照着深色模式手调过——那是长期在用、反复调过多轮的；浅色是 2026-07-30 才补的。以后调外观只动浅色那套，动深色属于要重新拍板的事。
- **不采用 macOS 26 的原生「液态玻璃」。** 实测过：在任务条这个尺寸上它带来的是更高的通透度和边缘高光，**并没有折射**；而那个通透度实测**太透了，图标反而不好认**。所以不用它，任务条继续用自己调的毛玻璃，macOS 12 起的所有系统版本观感一致。
- **玻璃折射做不出来，这是平台限制、不是我们的取舍。** 毛玻璃的合成是系统自己在窗口后面完成的，应用**拿不到自己窗口背后的那些像素**——没有原料，就无法把背景按曲面挪位置。苹果自己的控件能做是因为它就跑在系统合成器里。唯一的绕法是应用自己持续截屏再变形，代价有三条：要多向用户要一个「屏幕录制」权限（比辅助功能更敏感）、截屏有帧延迟（任务条常驻置顶，背后窗口一动就会看出错位，比不做更糟）、还耗电。**明确不做，以后不必再评估。**
- **图标不再按状态变淡了（2026-08-02 定，浅色深色一起拿掉）。** 图标永远原色原亮度，「最小化」和「已退出」都不再淡化。
    - **反转的是 2026-07-30 那整套设计**（浅色靠降饱和、深色靠褪透明）。owner 实机用下来的判断：降饱和看着不舒服，而且**两档根本分不清哪档是哪档**；退回褪透明在浅色下又发灰。两条路都试过、都不行，就不做这个区分。
    - **区分本来就不该由图标扛**——这条 2026-07-30 就写下了，只是当时没走到底：图标下方的运行点已经在表达「是否运行」（退出无点），带标题的窗口卡还有标题颜色深浅表达「在不在桌面上」。**系统程序坞自己也是这么做的**：图标永远全彩，只用小圆点表示在运行。所以拿掉不是妥协，是回到系统惯例。
    - **已接受的代价**：单窗口应用最小化后，卡片和没最小化时长得完全一样（多窗口的卡还有标题颜色兜底）。
    - **什么时候重新考虑**：只有当「最小化的窗口在条上找不着」真的开始烦人时。那时的第一选择是**改运行点的样式**（在桌面=实心点 / 最小化=空心环 / 已退出=无点），把信号集中到一处，**不要回到图标淡化**——那条路已经花了两轮、两种做法都被否掉。
    - 旧数值记在这里以便复原：浅色 hidden `opacity 0.80 / grayscale 0.45 / brightness -0.02`、notRunning `0.72 / 0.58 / -0.03`；深色 hidden `opacity 0.45`、notRunning `0.35`（纯透明度，无滤镜）。
- **悬停效果做成可选（2026-08-02 加）。** 菜单上是**单个勾选项「鼠标悬停显示应用名」，默认勾选**（= 原样，升级用户零变化）。取消勾选 = 下文说的「安静档」。
    - **为什么值得做成设置而不是直接调**：原来那套是照原生程序坞的活泼手感做的，有人就是喜欢；但它有个实打实的副作用——**带标题的窗口卡悬停时会冒出应用名副标题，副标题一宽，整张卡就变宽，它右边所有卡片跟着平移**。任务条只是被鼠标路过就整行动一下。仓库里那套「像素前后对比」的方法论专门写了「测之前先把鼠标挪开任务条」，就是被这个坑过。两种口味都成立，所以给选择，不替用户拍板。
    - **「安静」档（= 取消勾选）的定义是"完全静止"，不是"少动一点"**：图标不缩放、不移动、不冒名字，胶囊底色也不提亮。实测确认：鼠标停在任意格子上，整条任务条**逐像素零变化**（0/255）。中间挡过一版「保留一层淡底色高亮」的折中，你选了彻底不动。
    - **四条边界，各有各的理由**：
        - **固定文件夹格 / 中转格一起关**——这档的意思就是「鼠标划过任务条什么都不动」，留着一半会显得只关了一半。
        - **长标题的全文浮层两档都保留**——它不是装饰，是标题被截断后看全文的**唯一**途径，而且它浮在条上方，不移动任何卡片。实测：安静档下停在被截断的卡上，卡片本身零变化，浮层照常弹出。
        - **抽屉入口胶囊（九宫格预览）不关**——它是抽屉的按钮，跟抽屉一起维持原样。
        - **抽屉面板里的图标不关**——抽屉是网格布局，悬停冒名字在那里是有用信息，不是干扰。
    - **已接受的代价**：安静档下中转格的件数不再显示（原本只写在悬停文字里），改由系统 tooltip 兜底。
    - **菜单名字有意只说了一半，这是拍板过的，不是漏写（2026-08-02 当天改名）。** 最初叫「悬停效果 ▸ 标准 / 安静」，你的判断是**只说了氛围、没说到底会变什么，一般用户看不懂**——这个 app 是公开发布的，菜单得让没读过说明的人看懂。改成勾选项时我提过异议：这个开关不只管应用名，取消勾选后**图标也不再缩放、固定文件夹格也不再放大**，所以「鼠标悬停显示应用名」承诺得比实际少，属于 8 月 2 号你自己砍掉「隐藏系统 Dock」那个命令的同一类毛病（名字和行为对不上），只是方向反过来。完整版名字（「悬停时放大图标并显示名称」）也备选过，你复议后仍然选了短的——理由是**「应用名」是这个效果里最显眼、最容易被一眼认出的那件事**，长名字读起来更累。
        - **给未来的人**：看到名实不符**不要当 bug 修**，尤其不要为了对齐名字去「只关掉名字、把图标缩放留着」——那样等于砍掉这一档的核心价值（鼠标只是路过就整行重排）。要改就改名字，不改行为。
    - **什么时候重新考虑**：如果安静档用久了觉得「不知道点没点中」，第一选择是**给安静档加一层不改尺寸的淡底色**（不改尺寸就不会重排，那是这一档的底线），而不是把缩放放回来。真加了第三档的话，菜单要从勾选项退回二级菜单，底层枚举一直是三档结构，不用改数据格式。
- **没经你看过的视觉效果一律默认关闭**，装机给你看、认可之后才转成默认。2026-07-30 有过一次教训：同一天做的三个效果，两个默认开了，你的界面在不知情的情况下偏离了你点过头的那版，是你自己发现的。（悬停效果这次默认就是原样那档，没有偏离。）
- **已接受的边界**：底板通透度、背景颜色浓度、玻璃厚度感三样做成了可调项但**默认关闭**。想再试随时能开，当前定稿不启用。

## 性能与手感的取舍（2026-07-31 的判断，**依据不硬，可以复议**）

- **已经做掉的**：「反馈计时器按需运行」，零可感知变化，空闲 CPU 降了 46%（2.60% → 1.40%）。真正的浪费不在计时器本身，而在它每 0.5 秒把一份界面上没人读的数据无条件写一遍，害得整条任务条每秒重算两次。
- **暂时没做的**：把三个后台轮询降频（前台窗口检测、最大化避让、消息角标）。当时的理由是「不拿可感知的延迟去换空闲 CPU」——那三样天天能感觉到，空闲 CPU 不是。
  - **决策反转**：一开始同意纳入（当时只看到"能降多少"），听完延迟代价后反转为「只做零感知的那一项」。

### ⚠️ 这个判断有多硬：不太硬

拍板之后，那三项的方案又被评审改过，**代价比拍板时看到的小**：

| | 拍板时看到的 | 评审修正后 |
|---|---|---|
| 消息角标 | 红点最差晚 1 秒 | **那条方案本身是错的**，已撤销。剩下的门控**零感知**——见下 |
| 前台窗口检测 | 标题最差晚 2 秒 | **1 秒**，而且要「标题原地变了 + 系统通知没报 + 屏上窗口没变」三条同时成立才降级 |
| 最大化避让 | 初次抬升最差晚 0.4 秒 | 代价减半（慢档从 0.6 秒收到 0.4 秒） |

**更要紧的一点**：上面这些秒数**全都是从代码里的常量推算出来的延迟，不是真人用过之后的手感结论**。0.2 秒的平均延迟到底能不能被察觉，**没有人测过**。所以这个判断的依据是估算，不是实测。

### 角标那项其实没被否

它的方向是**零感知门控**（任务条隐藏、或没有消息应用时暂停轮询），不带任何延迟代价，待办卡还开着：Obsidian 看板 `进度看板.html#card=没有消息应用时暂停角标轮询`。被否掉的只是卡里写明的那个「变化率退避」——那条**假设错了**（以为红点总是你点开应用才被清掉，其实后台同步、另一台设备已读也会清）。

### 剩下两项的差别，别再打包看

- **前台窗口检测**：收益最大（占 CPU 采样 16.4%），而且修正后的降级窗口很窄。**三者里最值得复议的一项。**
- **最大化避让**：最可能真被感觉到（初次抬升要多等），而且有托举会话时另有一个 20 Hz 的高频检测**不受慢档影响**，结构收益本来就最小。性价比最差。

### 什么时候该重新考虑

- **重新测一次占比之后。** 空闲 CPU 降到 1.40% 是砍掉了"帧"，而轮询的开销一点没变——所以它们现在占剩余开销的比例应该大幅上升了。按旧数推算可能到七成以上，**但那是推算，1.1 之后没有人重新 profile 过**。测一次就不用猜值不值得。
- **想直接验手感的话**，别再从估算里拍板：做成环境变量开关、默认关着，自己用一天，有感觉就退回去。仓库本来就是这么干的（`DOCK_WINDOW_LIFT=0` 这类），工程规则里也写着「未验收的效果一律 opt-in」。
- **电池或发热变成真实抱怨的时候。**

三项的现状核实、硬约束和修正后的完整方案（含第一版三处错误的复盘）都存档在仓库 `Docs/26-idle-performance-polling.md`，复议时不必从头再来。

- **投影合并与名称缓存暂缓。** 它们省的是"每一帧的成本"，而已做掉那项消掉的是"帧数本身"——空闲时已经几乎不产生帧，收益提前被吃掉了。剩下的价值在拖动、开关窗口这类交互场景，而目前没有卡顿反馈。等真觉得拖动不跟手了再说。

## 已明确不做

- 不做常驻垃圾桶，也不为它引入完全磁盘访问等额外权限。
- 不做“选择任意应用加入抽屉”的应用选择器；收纳动作从正在使用的应用发生。
- 不做角标点击后自行拼装消息列表；点击仍回到应用本身。
- 不做持续的前台窗口常亮高亮，除非以后出现明确使用价值且不会误判。
