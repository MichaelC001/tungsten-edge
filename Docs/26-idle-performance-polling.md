## 2026-08-09 真空闲配对复测：排序整个反了

上面两列占比**都是在有人操作电脑时采的**。这次用 `HIDIdleTime` 硬门槛做了一轮真空闲测量
（两臂各静置 5 分钟预热 + 5 分钟窗口，`caffeinate -di` 包全程，结束时系统输入空闲
868s / 1639s，前台 app 数首尾一致；机器同时跑着 Contexts 3.9.0 作横向对照）。

| 臂 | 钨极空闲 CPU | Contexts 空闲 CPU |
|---|---:|---:|
| A：最大化避让**关**（出厂默认） | **0.546%** | 0.232% |
| B：最大化避让**开** | **0.970%** | 0.239% |

Contexts 两臂 0.232% / 0.239%，差 3% —— 测量可重复，两臂条件可比。

**真空闲下的归因**（60 秒 `sample`，主线程墙钟份额）：

| 计时器 | A 臂样本 | B 臂样本 | B 臂占比 | 折算 CPU |
|---|---:|---:|---:|---:|
| 最大化避让 · 全局扫描（5 Hz） | —（关） | **348** | 42% | ≈0.41 pp |
| 座位对账 `reconcile`（0.2 Hz） | 233 | 247 | 30% | ≈0.29 pp |
| 消息角标（2 Hz） | 207 | 197 | 24% | ≈0.23 pp |
| 前台窗口轮询（2 Hz） | **35** | **27** | **3%** | ≈0.03 pp |
| 主线程总样本 | 47034 | 46796 | | |

交叉验证：避让那一项的归因换算（0.41 pp）与 A/B 实测差值（0.970 − 0.546 = 0.424 pp）
吻合到 3% 以内。`reconcile` / 角标 / 前台三项在两臂间几乎不变（233↔247、207↔197、35↔27），
说明避让是纯增量。

**结论修正，两条都要带走：**

1. **前台窗口轮询在空闲期几乎不花钱（≈0.03 pp）。** 本文第二节把它称作「三项里最值得做的一项」
   是基于污染数据的误判。owner 2026-07-31 否掉它的降频，事后看是对的——那是拿切标签的手感去
   换千分之三个 CPU。**这个候选应当永久划掉**，除非将来要优化的是"使用中"而非空闲。
2. **角标不是最小项，是第二大项（24%）。** 本文第三节「收益天花板约 0.08 个百分点，优先级最低」
   同样是污染数据的产物；真实量级约 0.23 pp。

方法论教训已登记进 `28-process-pitfalls.md`（归因采样必须同样过 HIDIdleTime 门槛）。

## 表外还有一笔：运行态兜底对账（2026-08-04 新增，**不是计时器**）

`RunningApplicationStore.reconcileWithWorkspace()`。**没有常驻计时器**，靠事件驱动：应用启动 / 切换 / 退出各触发一次（≥2s 节流），系统唤醒与解锁**强制立即**跑一次（那两个时刻正是退出通知最容易丢的边界）。

一次的动作：枚举 `NSWorkspace.runningApplications`，对每个有 bundleID 的进程读 `activationPolicy` / `isHidden` 并采一次 POSIX 代际（`kill` + `sysctl`），再为「被跟踪但本轮没观测到」的 pid 补采。**全在主线程。** 实现上有意只采一遍代际——观测里那份直接复用；早先的版本对同一批 pid 采了两遍，几十上百个进程 × 两个系统调用，纯属白花。

之所以宁可事件驱动也不加第五个计时器：这张表已经因为「以为列全了」被打脸两次。它在日常使用中的实际节奏 ≈ 每 2 秒一次（用户在切应用），空闲时**完全不跑**。**没有实测占比**——如果哪天重启降频讨论，这一笔要一起进表量，别再漏。

## 一、最大化避让

### 硬约束（已核实，不是推测）

- **`appReassertWindow = 1.0s`（`WindowLiftAvoidance.swift:33`）是时间尺度判定的核心。** 轮询周期一旦逼近 1 秒，应用抢顶就可能发生在两次采样之间、被误判成「新的用户会话」——正是 AGENTS 点名不许破坏的 L↔M 缩放记忆死锁。
- **`standoffRounds` 是事件驱动的**（观察到铺满在 `appReassertWindow` 内重现才 +1），不按 tick 计数 → 改周期**不会**改变退让上限的实际含义。
- **有 session 时另有一个 20 Hz 的 tracked probe**（`trackedSessionProbeInterval = 0.05`，`WindowLiftAvoidance.swift:26`）。对日常挂着最大化窗口的用户，常驻成本是它，而慢档**对它完全无效**。

### 2026-08-09 落地设计

- 一次性 TextEdit 探针用真实窗口拖拽 tracking 路径验证：`.commonModes` 下拖拽过程中连续实时收到 moved 通知，不是松手后补发；仓库已有 `FullscreenIntentMonitor` 的同形生产实现。
- `FrontmostWindowGeometryObserver` 只绑定前台 app 的 focused window。启动、app 激活、focused-window change、window-created、moved/resized/destroyed 都请求扫描。
- 事件扫描是 leading + trailing：冷却期或 `scanInFlight` 期间收到的事件，扫描结束后必须补一次收尾扫描。
- 无会话空闲兜底 **1.0s**；`states` / `suppressedFrames` / `restoreTask` 任一存在即立即回 **0.2s**。快档下禁用额外事件扫描，避免原 5 Hz 与事件 5 Hz 叠成 10 Hz。
- 快档退回 1 秒慢档时再排一次最终收敛扫描。实机 A/B 抓到新 app 激活早于窗口 settle：首次扫描命中、250ms 稳定性验证报 `candidateMoved`；若直接退慢档会多等 1 秒，最终扫描让同一毫秒就重试，保住旧固定 0.2 秒 timer 的收敛语义。
- **20 Hz tracked probe 完全不动**。设置关闭、stop 和权限冻结会拆 observer、event timer 与 pending coalescer。
- 1 秒权限自检只发生在没有窗口快照要保护的空闲期；任何会话/抑制/还原状态仍保持 0.2 秒。

### 落地后真空闲复测

同一个 Release 构建重新做 A2/B 配对（各 5 分钟预热 + 5 分钟窗口，前台都为 Contexts，
前台 app 数都是 11）：

| 臂 | 钨极空闲 CPU | Contexts 空闲 CPU |
|---|---:|---:|
| A2：最大化避让**关** | **0.576%** | 0.242% |
| B：最大化避让**开**（事件驱动） | **0.691%** | 0.259% |

**同config还测过第三个臂 `post-A`（避让关）＝1.298%，已排除**：它干净通过了 `HIDIdleTime` 门槛，
但前台窗口轮询是其它臂的 38 倍（1033 样本 vs 27/42），说明那 5 分钟屏幕上有后台应用自己在
开关窗口——不是代码变贵（该臂避让相关栈为 0 样本）。方法论见 `28-process-pitfalls.md`。
**归因侧独立验证**：避让扫描样本 **348 → 84（−76%）**，与下面的 CPU 增量降幅互相印证。

新实现中避让的配对增量为 **0.115pp**；改造前配对增量是 **0.424pp**，下降
**0.309pp / 73%**。开启避让的整进程数字从改造前 0.970% 降至 0.691%（−0.279pp / 29%）；
这后一组是跨配对比较，只作为量级交叉验证，不替代前面的同轮 A2/B 结论。60 秒归因中，
A2 没有避让扫描栈，B 能看到 1 Hz 全局扫描；前台应用在测量结束后再次确认为 Contexts。

### 角标事件探针结论

对 Dock application、AXList 和全部 AXDockItem 注册 `AXValueChanged` 均返回 `kAXErrorNotificationUnsupported`。因此没有事件保底，**不实施 2 秒退避**；角标继续 0.5 秒轮询，零感知门控仍是唯一可接受方向。

## 二、前台窗口轮询（三项里最值得做的一项）

### 注释债（可随手修，无行为影响）

`AppTracker.swift:989` 写着「单窗口 app 无歧义，直接跳过，平时零开销」——**这条注释是过期的**。原始实现（`88fef1d`）确实有 `app.windowOrder.count > 1` 这个跳过，inventory-first 重写时丢了，注释留了下来。今天它对单窗口前台 app 也是全量跑，**不存在"零开销"**。

### 硬约束

- **不能把 `windowOrder.count > 1` 搬回来。** 今天一个原生标签组 = 一个座位，搬回来会让 Ghostty 类切标签失效。
- **`captureOnScreenWindowIDs()`（`CGWindowSnapshot.swift:16-24`）查询失败时 `return []`**，与"真的没有 layer-0 窗口"无法区分。连续两次失败会读到"空 == 空"而错误跳过完整对账。要用它做判据，**必须先把返回值改成可选**，把失败与空集分开。
- **`reconcileSeats` 远不只是标题。** 它同时承载最小化状态、shadow pool 轮次（AGENTS 要求判定用**上一轮**的池）、`formerCgIDs` 与 CG 全表求交清理、屏外关闭、phantom 判定输入。放宽它的节奏 = 把这些一起放宽。

### 修正后的设计（若将来实施）

- 每 tick 保留 0.5s 的 on-screen 便宜信号（**切标签响应不变**）
- 完整对账兜底取 **1 秒**（不是 2 秒），且按**单调时间**判断而非 tick 数
- **四者任一都必须走完整 capture**：前台 pid 变化 / on-screen 集合变化 / 快速查询失败 / 距上次完整对账满 1 秒

## 三、消息角标

### 硬约束

`BadgeStore.swift:5` 的注释明确写着产品要求：**清掉未读角标必须即时**。

### 修正后的设计

**只做零感知门控**：任务条逻辑隐藏、或没有可见消息入口时暂停轮询，恢复显示时立即读一次；可见状态下保持 0.5s，**不做退避**。

收益天花板约 0.08 个百分点，优先级最低。

## 四、第一版设计的三处实质错误（本文最有价值的部分）

这三条都是 Codex 评审指出、经核实成立的。写下来是为了下一轮不重犯。

**① 避让：频率表整个漏了 20 Hz 的 tracked probe。**
只看到 5 Hz 全局扫描就去设计慢档，而对日常挂着最大化窗口的用户，常驻成本恰恰是那个 20 Hz probe，慢档对它无效。**教训**：给一个子系统做降频前，先把它**所有**计时器列全，别只抓最显眼的那个。

**② 前台：把「跳过完整对账」轻描淡写成"标题兜底"。**
实际放宽的是最小化状态、shadow pool、`formerCgIDs` 清理、屏外关闭、phantom 判定一整套。**教训**：一个函数叫 `reconcileSeats` 就别当它只做一件事——先读它到底改了哪些状态，再谈能不能少调。

**③ 角标：变化率退避建立在一个错误假设上。**
原话是「清红点总跟在激活该 app 之后，所以前台切换这条钩子正好守住产品要求」。**这是错的**：后台同步、另一台设备已读、应用后台处理都会清角标，与前台切换无关。而且"立即读一次"还可能抢在应用真正清除之前，随后仍要再等一个退避周期。**教训**：把"用户行为总是伴随 X"当成守卫条件之前，先列全不经过 X 的路径。
